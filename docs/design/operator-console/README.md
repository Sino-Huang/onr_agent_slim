# Operator Console v2

The Rust ratatui console is a loopback HTTP client of the Python Runtime Host, not a process launcher. The Host launches one per-run Environment Stack through the Run Worker (ADR [0015](../../adr/0015-runtime-host-per-run-environment-stack.md)); environment state stays environment-authoritative. The console requires Runtime Host API **1.2 or newer in major version 1**; the Host serves **1.3**, whose AirSim additions a 1.2 Host simply lacks. There is no legacy dashboard fallback. The Host keeps its v1.0 endpoints for other clients.

## States and ownership

```text
Connecting → Launch / Editing → ReviewActivation → Submitting → Run
                  ↑                    │                       │
                  └──── Escape ────────┘                       │
                  └──── e (rejected or finished run) ──────────┘
```

- A Console Session is persisted under `~/.local/state/onr/operator-console/session.json` (respecting the platform state-directory override). Its credential authorizes intent readback, activation and cancellation. Observers cannot cancel another session's run.
- Review assigns an Activation Request ID. A retry of the same intent **and stack selection** reuses that identity; editing either creates a new activation identity. `e` after a finished run discards it, so relaunching the same intent (for example after a stack failure) is a new activation, not a replay of the finished run.
- The Host permits one nonterminal Mission Run. Cancellation stops only processes launched for that run, never an independently started environment.
- `q` and Ctrl+C use managed exit during an active owned run. The cancel confirmation is not bypassed by Ctrl+C. While the Host is stale or offline, Ctrl+C cannot cancel and says so.
- Ctrl+Q is the explicit detach: the console quits without cancelling, releases a Host it bootstrapped without stopping it, and keeps the persisted owner credential, so a relaunch recovers the run.
- A bootstrapped Host runs in its own process group with stdin closed and output in `var/runtime-host/host.log`, so a console SIGKILL or terminal hangup leaves the Host and run alive; relaunch recovers the persisted session. A relaunched console finds that Host already healthy and never stops it on exit.
- If a managed exit's 15 s cancellation wait expires, the console quits and stops a Host it bootstrapped. The next Host start finishes reaping and records `cancelled_by_owner` if the Host had accepted the cancellation, otherwise a Host-Interrupted Failure.
- A Host killed unexpectedly leaves the Run Worker (its own session) orphaned. On restart, the Host proves ownership by the persisted worker PID plus process start time or by the exact run-ownership token, reaps the worker group and token-carrying detached groups (never the Harbor restoration guardian), and records a Host-Interrupted Failure, or `cancelled_by_owner` when cancellation was already requested. Zombie-only process groups are not live.
- An absent or superseded recovered owner run returns to actionable Launch. It never grants cancellation authority over a different run or strands the console in Connecting.
- Stale/offline liveness and terminal restoration remain separate from run status. See [terminal-lifecycle.md](terminal-lifecycle.md).

## Launch

The Launch screen presents preset, AirSim, perception (`off`, `ideal`, `yolo`), update ownership, simulation limit, Mission Intent and live Preflight Checks. The intent starts with the preset's actual default mission text. Changing a stack selection schedules a debounced preflight refresh (300 ms); launch is disabled while checks are pending or failed.

Preflight is a focusable region in the Tab cycle (after Sim limit, before Mission Intent). It lists one row per check, failures first, then warnings, then passes (the Host's order within each group), with counts in its title (`Preflight · launch blocked · ✖1 ▲1 ✔10`) and the shared scrolling-list position and `▲`/`▼` overflow marks. A row that does not fit is cut with `…`. With Preflight focused, ↑↓ (Home/End) select a check and Enter opens its full detail: label, status, `check_id`, detail, hint, and the Host's optional diagnostic command (`remediation`), shown as copyable text the console never runs. ↑↓ step through checks inside the detail; Esc returns; `r` re-runs preflight from either. The selection is kept by `check_id` across refreshes; when its check disappears the selection returns to the first check and an open detail closes. In the Mission Intent editor every letter, including `r`, is text. Frames: `launch-preflight-focused-*`, `launch-preflight-check-*`.

Preset support is authoritative: perception requires AirSim. AirSim has two mechanisms (ADR [0016](../../adr/0016-airsim-follower-and-perception-annotations.md)): with perception off the AirSim Follower visualizes the simulated world model (`mission1-harbor` and `mission1-airsim`); with `ideal`/`yolo` the scene clock synchronizes the world model to the recorded engine scene (`mission1-airsim` only). Unsupported combinations are excluded and the preset's `unsupported_reason` explains why. `joint` requires a configured Mission 1 report instance; preflight reports this prerequisite rather than inventing an input.

F2 opens the demo-prompt picker: the preset mission, `buy me a coffee`, `What is the capital of France?`, and gibberish. Alt+Enter (Ctrl+Enter where reported) reviews; Enter in review launches. Bare Enter in the intent editor adds a newline. Tab selects a field; Left/Right changes a stack field.

"What this runs" sits between the Stack/Preflight row and the Mission Intent editor and follows the selected preset and toggles. Each row is a Host-authored description from the preset catalog (`conf/stack_presets.yaml`), never console text: **Mission** (the preset's goal and whether real LLM calls happen), **Truth** (the perception choice: simulated truth, or perception-fed truth from ideal perception or YOLO), **AirSim** (the AirSim choice under the current perception: nothing, the AirSim Follower visualizing the simulated world with no agent perception, or the scene clock's annotated front camera) and **Updates** (what Mission time does against wall time; in coordinator-driven mode it pauses while agents reason). Focusing Updates lists every update mode with its description, the selected one marked `▸`. An older Host sends no descriptions: the panel is absent, and the console invents none. The panel takes its rows after the Stack panel and before the scrollable Preflight list may grow, so the editor keeps at least 3 rows at 100×30 (5 in the default selection).

Enter on Preset opens the named preset picker (`frames/launch-preset-picker-*.txt`): every preset by title and id, the current one marked, and for the highlighted one its description, mission mode, the toggles it offers and the defaults selecting it applies. ↑↓ (Home/End) move, Enter selects, Esc cancels; re-picking the current preset keeps the operator's toggles. Left/Right still cycle presets.

## Run surface

The header combines Mission Run lifecycle, mission time, FSM state, Active Maneuver and stack health. The phase stepper uses code-owned evidence mapping: Stack → Intent → Planning → Statechart → Executing → Done. A rejected mission fails the Intent step; later steps remain pending.

### Progress and importance

The narrative is the tree root. Each summary is a parent over its `input_start_sequence`–`input_end_sequence` records. Uncovered records sit under **Live — not yet summarized**. When a summary arrives, the Host emits updated nodes with the same IDs and new parents; the console merges in place. The narrative and summaries carry an **AI** badge and are non-authoritative.

The narrative header says how fresh the narrative is and what it covers: `AI narrative · 42 s old · through record #763 · 18 newer`. The age is wall time since `generated_at` and ticks between polls; `through record #N` is the narrative's `source_watermark` (an operational-log record sequence); `N newer` is `latest_operational_sequence − source_watermark`, shown only when the Host reports `latest_operational_sequence` (v1.5), so an older Host shows coverage without a count rather than a guessed one. Before a narrative exists the header reads `AI narrative · coverage pending`; the run's final attempt adds `final` (and drops a `0 newer` count); a failed attempt reads `unavailable · attempted 12 s ago`. The Overview preview caps the narrative at 4 wrapped rows and points to Progress, where the root node's detail pane shows the full text with `through record #763 · newest record #781`. Frames: `run-overview-narrative-*`, `run-progress-narrative-*`.

Initial activation and recovery hydrate all nine sections, drain older pages using `before_cursor`, then replay forward deltas from the initial watermark. Backward pages add only unseen IDs, so historical snapshots cannot undo newer reparenting or paused selection. Terminal completion waits for both history and forward pages. Progress nodes are ordered by their semantic ID's kind and numeric sequence (`log:9` before `log:10`), so newest-first recovered pages still navigate chronologically.

Importance is mapping version 1, assigned by Python code, not by the model. A summary takes the highest importance of its covered records.

| Level | Glyph | Colour |
| --- | --- | --- |
| critical | ✖ | red, bold |
| warning | ▲ | yellow |
| notable | ● | green |
| routine | · | default |
| debug | ∙ | dark grey, hidden by default |

Component badges: HYP, MAN, CC, FSM, BEL, ENV, PER, STK. Glyphs remain visible with `NO_COLOR`.

### Belief and context truthfulness

Reporting-reliability entities include mean, honest probability, credible interval, variance, outcome counts, deltas and bounded revision history. Mission 2–4 report explicitly that no Bayesian belief service is composed for that mission mode. Mission 4's environment-owned object-search belief is not presented as agent-storage evidence.

Mission Snapshot source freshness is a boolean per source, not an invented age. FSM candidates are the actual enabled-candidate list. A maneuver gauge is shown only when progress provides a computable fraction (for example cleared search cells); distance-only navigation remains a distance readout. Pending perception count is omitted because it is not persisted in transport.

### Layout and keys

Compact at 100×30 (image hidden), standard at 140×40, wide at ≥180×50. Panes grow with the terminal; there is no fixed 100×30 drawing canvas.

- `1`–`7`, Tab/Shift+Tab: switch run tabs.
- `?`: help; Escape closes overlays.
- Up/Down or `j`/`k`: select; Left/Right: fold/unfold the progress tree.
- Progress: `f` follow newest, `i` minimum importance, `/` search, `n`/`N` next/previous match. Search editing captures letters, digits and Tab until Enter/Escape; Ctrl+C remains managed exit.
- World: `s` cycles world → annotated front → front → third-person, skipping sources without a frame; `p` pauses display fetching.
- Agents and Artifacts lists: the viewport keeps the selection visible, shows its position (`37/142`) on the bottom border and marks hidden rows with ▲ (top border) and ▼ (bottom border). Selection is kept by stable ID and the viewport offset is kept across evidence updates and resizes; Home/End jump to the first/last row.
- Agents: `f` follow; moving the selection (including End onto the newest row) pauses following and only `f` resumes it; PageUp/PageDown scroll detail.
- Artifacts: Enter inspect. In the inspector, Up/Down (`j`/`k`) and PageUp/PageDown scroll the wrapped lines of the current byte page, Home/End jump to its first/last line; Right/`n` next 4096-byte page, Left/`p` previous page (each opens at its first line); Escape close. The status row reads `line 12/83 · bytes 4096-8191 of 51234` (first visible wrapped line; inclusive byte range); the line position survives refreshes of the same page and resizes.
- `c`: owner-scoped cancellation; `q`/Ctrl+C: managed exit; Ctrl+Q: detach without cancelling.
- F3 (Launch or Run): run history; Enter opens a run read-only with a `HISTORICAL` badge, Escape returns (see the v1.5 surfaces below).
- F4 (Run): the presentation layout over the current tab; `v` next evidence card, `p` freeze/resume, `s` World source, F4 back (see below).
- Rejection card: `e` edit a new intent with the same preset/toggles once cleanup ends; Enter inspect the rejected run. The card can appear while final summaries and teardown are still in progress.

### Attention signals

Long waits need no watching. `app::attention` is pure edge detection over the run record and `overview.phase`: the `stack` step turning `done` (stack ready → planning started), a stack failure (`stack` step `failed`, or a `stack_failed` terminal classification/detail), status `awaiting_human_decision`, and a terminal status. Each kind fires once per Mission Run (run id + kind). On a run the console activated in this process every transition is new; on a run it first sees through owner recovery, a condition already true at its first observation is recorded as fired without an event, so a restart never replays a bell. Once the run is terminal only the terminal event is emitted; a stack failure first seen as the terminal status is that one event. Nothing is persisted: the first-observation rule is sufficient, at the cost that a second Human Decision Request after a console restart alerts again.

`main.rs` turns events into terminal writes outside drawing (see [terminal-lifecycle.md](terminal-lifecycle.md)). The title is a status display in every mode (`ONR ● running 00:12:04 · Planning`, `ONR ✔ succeeded`, `ONR ✖ stack_failed`). `--notify none` writes only the title; `bell` (default) adds one BEL per batch of events; `desktop` adds one notification per event: `OSC 777 ; notify` when `VTE_VERSION` is set or `TERM` is `rxvt*`, otherwise `OSC 9` (one protocol only, because terminals that implement both would notify twice). Inside tmux (`TMUX` set) the desktop sequence is wrapped in DCS passthrough, which tmux 3.3+ forwards only with `allow-passthrough on`; the title becomes `#{pane_title}` and a bell in a background window sets `#{window_bell_flag}`.

### Presentation layout

F4 (`app::presentation`, `ui::presentation`; `frames/run-presentation-*`) replaces the tab chrome with a presenter's view of the displayed run: the mission title (preset catalog title, else preset id, else mission id), the wall clock in UTC with the run's wall time and Mission time, the phase stepper and waiting banner, live alert rows, the selected World source (shared `WorldMedia`, scaled up to fill) with the AirSim disclosure rows of the World tab (`AirSim:`, `Overlay:`, `Boxes:` — ADR 0016), and one evidence card. The card reads the existing selections and nothing rotates by itself: the milestone (current phase step plus the Progress selection), the Belief/Context entity (drawn as on its tab), or the Agents invocation; `v` cycles the kind. The selected tab stays selected behind the layout and F4 returns to it; tab keys, `w` and the failure card's `l` leave the layout. While shown, polling follows the layout's sections (Overview, Progress, Beliefs, Agents, World) and the frame; a parked inspector is not polled.

`p` freezes the display only: a copy of the evidence on screen (Mission time, phase, card data, world disclosures) and the wall clock and run time at the freeze are held, and the clock row reads `FROZEN AT <wall> · t=<mission>`. Every section keeps polling into the live view, so resuming shows the latest at once. The frame is held through the World tab's `p` (`WorldMedia::paused`): no frame fetch while frozen, a reply already in flight is dropped (releasing its post-terminal refresh claim), the World page does not switch the source, and resuming restores the pause state the freeze found. `s` is refused while frozen. Alerts are derived live from the current run and Host liveness, never from the frozen copy: a failed run or failed `stack` step (the U3 stack-failure and U7 failure-card sources; the failure card draws over the layout), `awaiting_human_decision` (the U3 source), and a stale or offline Host. A historical run can be presented read-only (its refused keys stay refused); its alert rows follow the parked current run, which keeps its lifecycle polling. Contract: none.

## HTTP and concurrency

Control, evidence and media workers use std threads and bounded/coalesced request queues; ureq HTTP never runs in drawing. On terminal status, all sections are drained once; Overview then refreshes at 2 s while the terminal narrative attempt finishes (`available` or `unavailable`). A synchronized final section wave drains every remaining page, then polling stops. Media is fetched only while visible, at roughly 2 Hz; decoding and protocol resize/encoding are off the UI thread. Cancellation has a 12 s HTTP deadline and a 15 s managed wait because owned-stack teardown can take up to 9 s; ordinary requests keep their 5 s deadline.

It shows the stage (the failed phase step plus `terminal_detail.stage`), the sanitized reason, the failed service (`terminal_detail.service`, else the stack's `failed` services, labelled as such), the last `done` phase step, the cleanup state (no service `starting`/`ready`/`stopping` in the stack section), the run id and Run Root, and the stack status's `last_line` of the chosen log labelled "context only, not the cause". `l` opens that log in the Artifact inspector at its tail (first page, then the last byte page, scrolled to the last line; ← steps back a page width); with an older Host it falls back to the failed service's `log_artifact_id` from the stack status, else `worker-log`, and says so. `2` opens Progress; `y` queues `<run id> <run root>` and the run loop writes it as OSC 52 (inside tmux also wrapped in DCS passthrough); Enter or a tab key dismisses; `e` stays on the run until cleanup is confirmed. A terminal detail whose `kind` differs from the classification (a rejection published before a Host restart) is not used for the card.
- Teardown (#76 U8). Stack `services[]` entries add state `stopping` and optional `stop_requested_at` and `stop_grace_seconds` (the Stack Supervisor's SIGTERM-to-SIGKILL grace for that service), present once teardown signalled the service, plus `stop_mode` (`graceful`: exited within its grace; `forced`: SIGKILL after it, or reaped by the Host with the Run Worker's process tree before the supervisor saw it exit; the Host cannot tell whether such a service was already exiting, so it never claims graceful) and `stopped_at`. The supervisor rewrites `stack-status.json` as each running service turns `stopping` and again once it is `stopped`, in reverse start order; a service that already `failed` (readiness timeout) keeps that state. An owner-cancelled closed loop ends `stopped`, not `failed`. The `stack` object adds optional `teardown`: `started_at`, `finished_at` (`null` while stopping), `stop_order` (the services teardown signals, in order), and the Host's receipt fields `worker` (`running` | `stopped`: the Run Worker returned from teardown, or the Host verified its process tree exited) and `harbor_config` (`state` `confirmed` | `unknown` | `not_applicable`, `reported_by` `engine` | `guardian` | `null`). `confirmed` requires `live_engine`'s own restoration line in `services/airsim-engine.log` without its restoration-failure line (the engine compares the restored bytes with the originals) or the guardian's line in `engine/guardian.log`; it is read on each request, so `unknown` can turn `confirmed` once the guardian finishes. `not_applicable` means no `airsim-engine` started. A forced Host reap marks every `ready`, `starting` or `stopping` service `stopped` with `stop_mode: forced` and `stopped_at` at the verified exit (the Host's timestamp format), keeps the modes the supervisor already recorded, and sets `teardown.finished_at` (creating `teardown` with `started_at: null` and an empty `stop_order` if the supervisor never began). The Host waits about 7 s after SIGTERM to the Run Worker before reaping, so with AirSim the engine, which the supervisor stops last with a 30 s grace, is often recorded `forced` while its own log still reports the configuration restored. Examples: `mission-run-operator-stack.stopping.response.json`, `mission-run-operator-stack.cancelled.response.json`.
- The console's waiting banner gains a teardown mode that outranks every other wait: `Stopping airsim-engine (3/3) · 0:06 / grace 0:30` (position in `stop_order`, elapsed since `stop_requested_at`, `▲` after 80% of the grace), `Stopping the Environment Stack (2/3 stopped)` between services, and `Cancellation requested · waiting for the Run Worker to begin teardown` before the stack reports any. The Stack tab marks `◑ stopping` with `0:06 / grace 0:30`, shows `graceful`/`forced` on stopped services and a `Stop:` detail row. A terminal Overview with a `teardown` grows the Mission Run panel by a three-row receipt: `Teardown: worker stopped · took 0:10`, `Services: 3 stopped · 2 graceful, 1 forced`, `Harbor: config restored (guardian reported)` / `restoration unknown (no report)` / `not applicable (no AirSim engine)`. Frames: `run-teardown-*`, `run-teardown-stack-*`, `run-teardown-receipt-*`.
- Terminal receipt (#76 U9). `overview` adds optional `receipt` on terminal runs only (absent while running and from older Hosts): `status` and `classification` (the Run Worker's lifecycle, never a mission verdict), `wall_seconds` (start, or creation, to finish), `final` (`fsm_state` and `plan_revision` from the latest FSM status or execution record, `mission_time_seconds` from the environment evidence, `source` naming the record kind), `audit` and `export`. `audit.status` is `pass` or `fail` only when `scripts/audit_live_demo.py` wrote `live-acceptance.json` into the Run Root, `not_recorded` without that file and `unreadable` when it is not a PASS/FAIL audit; `path`, `recorded_at` (file mtime), `mission_mode` and up to 20 `failures` come from the file. The Host never runs the audit and never derives a verdict from the lifecycle. Cleanup stays in the stack's `teardown` receipt. `export` is `{path, exported_at}`: where `x` writes and the last export (`null`: never). Example: `mission-run-operator-overview.succeeded.response.json` (a succeeded lifecycle whose audit recorded FAIL).
- `POST /api/v1/mission-runs/{id}/receipt-exports` (v1.5, owner credential, loopback only; body `{}`, unknown fields `422`): the Host writes `<run root>/mission-run-receipt.json` atomically (unique temporary file, then rename) and answers `200` with `mission_run_id`, absolute `path`, `exported_at`, `byte_size` and `replaced` (an earlier export was overwritten; each export replaces the file with the receipt as projected now, re-reading the audit). A running run answers `409 mission_run_not_terminal`; another session or a remote client `403`. The file holds `schema_version`, `kind` `mission_run_receipt`, `exported_at`, the run ids, `run_root`, the `receipt` (without `export`), `terminal_detail`, the stack's `preset_id`, `teardown` and per-service `name`/`state`/`stop_mode`/`stopped_at`, and `artifacts`: Run Root relative `path`, `role` (`closed_loop_result`, `live_demo_audit`, `stack_plan`, `stack_status`, `observations`, `narrative`, `world_frame`, `log`), `byte_size` and, for logs, the `artifact_id` the Artifacts tab serves. Examples: `mission-run-receipt-export.request.json`, `mission-run-receipt-export.response.json`, `mission-run-receipt.json`.
- The console's terminal Mission Run panel becomes the receipt (title `Mission Run · receipt`): `Lifecycle:` (relabelled from `Status:`), `Finished: … · 5:12 wall`, `Final: FSM mission-complete · plan r4 · t=120.0 s`, `Audit: PASS · live-acceptance.json` / `FAIL · 1 failure: …` / `not recorded (no audit artifact)`, the U8 `Teardown:`/`Services:`/`Harbor:` rows, and `Export:` (`x writes mission-run-receipt.json`, then `✔ wrote` or `✔ overwrote` with the Host's absolute path broken after `/`, or the Host's refusal). `x` binds only on a terminal run, for the owning console, with a receipt; a second `x` while one is in flight is ignored. After termination the header shows `last <maneuver>` instead of `▶ <maneuver>`, and the Context (Overview mini and Belief/Context tab) labels the FSM state, maneuver and transition intent `last observed`. The receipt is read at the final refresh; an audit written later reaches the exported file (the Host re-reads it per export), and each written export refreshes the Overview once so the `Audit` row matches the file. Frames: `run-receipt-succeeded-*`, `run-receipt-failed-*`, `run-receipt-cancelled-*` (after `x`), `run-receipt-context-*`.
- Run history (#76 U10). `GET /api/v1/mission-runs?limit=&before=` (v1.5, loopback only like operator-view; other query fields `422`): `{mission_runs, next_before}`, newest first. Rows are ordered by `created_at` then run id, both descending; `before` is the last row's run id, so a newer activation never shifts or repeats an older page (`limit` 1–100, default 20; an unknown `before` is `422 invalid_cursor`). Each row is `mission_run` (the `/current` public record: ids, status, timestamps, classification, `stack`, `terminal_detail`), `toggles` (`update_ownership`, `simulation_limit_seconds`; `null` before v1.2), `wall_seconds` (`null` until terminal), `run_root_available` (the Run Root directory still exists) and `current`. Rows never carry the Mission Intent; it stays behind the owner credential of each run (`/mission-intent`). A historical run opens through the existing per-run routes (the Host reloads it from its Run Root and caches at most one requested historical run, ADR 0015); when its Run Root is gone every evidence route answers `404 run_root_unavailable` instead of an empty run. Example: `mission-runs.response.json`.
- The console's F3 overlay (Launch or Run, `frames/run-history-*`) lists the rows (start time, preset and toggles, status/classification, wall time, run id, `● current`/`◆ owned`/`✖ no root`) in the shared scrolling list, cycles a status filter (`s`) and a preset filter (`p`) over the loaded rows, and requests the next older page when the selection reaches the last loaded row. Enter on a `✖ no root` row explains the missing Run Root. Enter otherwise opens the run read-only in the normal seven tabs (`frames/run-historical-overview-*`): a `HISTORICAL` header badge, the receipt's `Export:` row read-only, `c`/`q`/`e`/`x` refused, Escape back to the current run or Launch. The current run's state (record, view, terminal-refresh bookkeeping) is parked, not replaced: `/current`, Overview and Stack keep being polled for it and reduced into the parked state, so its attention events and the window title keep following it, while a historical run never reaches attention. The owner session file, the activation and the owned run id are never touched.
- Cold historical reads (#76 U10). A Host rebuilds a run it has not served since it started from its Run Root (the cold reload under "Projection caches" below). For the 28-minute `run-998f35fe…` (696 MB Run Root) the first operator-view read took 17.4 s, almost all of it re-reading the transport topic files; a read sent while that rebuild is in flight answered in 1.7 s with the same page, and warm reads take 20–45 ms. The console keeps its 5 s request limit. Until the historical run's first Overview page arrives (Overview is read first, so it is the read that waits for the rebuild; other sections can answer earlier), the header shows `loading from disk N s` and the footer `Loading from disk · N s · first open rebuilds the Host's view`, plus `· K read(s) timed out, retrying` (`frames/run-historical-loading-*`). A timed-out read (`HostError::Timeout`, separate from other transport errors) is retried on the next poll without a notice. Any other error, and a timeout after that first Overview page, still raises the usual `Host <section> poll failed` notice. The footer notice belongs to its run context: whatever the historical view raised is dropped on Escape, and the current run's notice comes back, including one raised by its parked polls.

Contract examples live in [contract/v1.2](contract/v1.2), [contract/v1.3](contract/v1.3), [contract/v1.4](contract/v1.4) and [contract/v1.5](contract/v1.5); Rust serialization round-trips all four. Python owns importance, phase and run status. Narrative generation is asynchronous, on a 30 s cadence plus a terminal attempt; requests only read stored narrative records. Evidence ingestion is incremental and outside the Host's global state lock.

Projection caches are per Mission Run. The debug-artifact catalog reparses only discovered files whose metadata identity changed; the planner inventory lstats without following symlinks or reading content; environment evidence folds the latest FSM status, Maneuver Feedback and last ten belief events; the current environment state (position, Mission time, maneuver lifecycle) is the fake environment's `<mission>/environment.json` or the physical runtime's `<mission>/live/latest.json` under the run's environment artifacts; JSON evidence reads are size-capped and LRU-bounded. The Host keeps this state only for the current run, runs awaiting a terminal narrative, and one requested historical run; it prunes at lifecycle boundaries or a cache miss, never on steady polls. Pruned runs reload from their Run Root.

## Images

`ratatui-image` protocol selection: `--image-protocol auto|kitty|sixel|iterm2|halfblocks|off` or `ONR_CONSOLE_IMAGE_PROTOCOL`. Auto queries the terminal after initialization; halfblocks is the portable fallback inside tmux/herdr. Finished runs retain their cached final world frame under `world-frames/latest.png`; the Run Worker captures it after stopping camera capture and before stopping the stack.

For draw-latency measurements, set `ONR_CONSOLE_DRAW_LOG` to a file under repository `var/tmp`; each frame records elapsed drawing time in microseconds. This is opt-in diagnostic output, not mission evidence.

### AirSim cameras

Every AirSim run starts Harbor. Camera frames are persisted atomically as `world-frames/{camera_front,camera_front_annotated,camera_third_person}.jpg` with `.json` metadata (source, sequence, SHA-256 ETag, Mission time, camera and vehicle names, AirSim `sensor_timestamp_ns`; annotated frames add the `annotation` status and their `boxes`). State transitions go to `world-frames/camera-capture.json`; the `world.airsim` status is `world-frames/airsim.json`. Identical pixels, such as a paused scene, do not create a new generation. Live and terminal runs serve these files without network access; a camera image the viewer itself provides takes precedence while the run is live.

**Perception off — AirSim Follower.** The `airsim-visualizer` service owns the frozen engine's clock (ADR 0016). For each new world-model Mission time it steps the scene to `lead_in + mission_time`, re-measures ship playback against the fixture trajectories, teleports the drone to the world-model pose, flushes one 0.1 s render step and captures front Scene + Segmentation and third-person Scene at 960×540. The annotated frame draws ideal instance-segmentation boxes labelled `ship N` and the disclosure "AirSim follows the world model. Boxes are ideal instance segmentation, not agent perception." `lag_seconds` is how far the newest world-model state is ahead of the shown frame; `ship_phase_error_seconds` is the largest measured ship playback error in that frame. Visualization never gates the world model.

**Perception ideal/yolo — scene clock.** The Run Worker starts a read-only `CameraCapture` once every stack service and post-ready step has finished. A dedicated daemon thread calls only `simGetImages` at a nominal 2 Hz for vehicle `SimpleFlight`: `front_center_custom` → `camera_front` and `third_person_demo` → `camera_third_person` (`engine.airsim_camera` and `engine.airsim_third_person_camera` in `conf/stack_presets.yaml`), plus the front Segmentation image for ideal perception. It never enables API control, arms, moves cameras, pauses or writes the clock. The annotated frame shows the perception module's output for that frame only: YOLO boxes from `perception_audit.jsonl` matched by AirSim image timestamp (fallback: Mission time within the 0.25 s scene-clock sensor lag), or the ships ideal perception reported, outlined from the frame's segmentation. Otherwise YOLO frames read "no perception sample for this frame"; ideal frames read "ideal perception reported no ships for this frame", because ideal perception publishes only the ships it saw and an empty sample cannot be told apart from a frame between samples. Cameras absent from the AirSim settings report `camera_not_configured`. Teardown stops capture (bounded by one in-flight SDK request) before the final world frame and the stack stop; nothing is persisted after stop.
