Mission 1 · methodology briefPlanned experiment

Which ship reports
can we trust?

Mission 1 uses a drone’s limited observations to estimate which ships are more likely to send misleading event reports.

Important boundaryDuring the mission, the agent sees ship reports and what the drone can observe. It never receives the hidden ground truth.
01 / The real-life challenge

A report is a claim, not proof.

Ships report what they did: for example, that they changed lane or changed speed. Some reports can be wrong or deceptive. A single drone cannot watch every ship all the time.

The practical question is simple: where should the drone look next, and what should it learn from what it sees? The system compares a report with a visible event when the drone is in the right place at the right time. It then uses those limited checks to estimate a ship’s report-level deception rate.

Detection foundation

What the drone can confirm: a mismatch or a fabricated report when the ship is visible within the relevant time window.

What it cannot use: the environment’s Ground-Truth Events. Those remain internal so the agent cannot cheat.

02 / What we know at the start

A controlled experiment with clear limits

These are experiment choices, not observations or results. Each has a reason, and each has a clear consequence if reality later differs.

Planned

One drone, 20 ships, 300 seconds

Assumption

Each generated episode has one drone, 20 ships, and runs for 300 seconds.

Why reasonable here

It creates a real attention limit: the drone cannot continuously watch every ship.

What changes later if false

More drones or a longer mission would require a different scheduling and evaluation setup.

Known mission setting

Assumption

Why reasonable here

Assumed

Perfect controlled perception

Assumption

The world model is perfectly perceived; there is no Perception subagent in this experiment.

Why reasonable here

It tests the surveillance and belief idea without mixing in sensor error.

What changes later if false

Designed

Authored reports; hidden truth

Assumption

Event Reports and Ground-Truth Events are authored as separate streams. Ground truth is never agent-visible.

Why reasonable here

It keeps scenarios reproducible and prevents the agent from solving the task by reading the answer.

What changes later if false

If truth leaks, the experiment is invalid. If reports are not authored, scenario control changes.

Planned

15–30 second observation windows

Assumption

The planned experiment uses event windows of about 15–30 seconds.

Why reasonable here

The window gives the drone a limited but usable chance to observe a reported event.

What changes later if false

Shorter or longer windows change how hard coverage is and must be re-evaluated.

04 / What the system does

Four repeated decisions

1

Observe a ship

Fly to a place where a reported event can be checked.

2

Compare the report

If the ship is visible in time, compare its report with the event the world model sees.

3

Update that ship’s belief

A confirmed mismatch counts toward deception. A fully observed window without one counts toward an honest report.

4

Choose who to watch next

Prioritize useful checks while respecting where the drone can feasibly travel.

Technical detail

The Hyper Agent keeps the per-ship Beta belief for this controlled experiment. MiniZinc helps make a feasible patrol and reactive schedule. This is a planned configuration; the experiment does not add a Perception subagent. GitHub issue #21, flow and decisions; docs/adr/0003-mission1-belief-ownership-simplification.md:5–30

05 / System output

A short list of ships that need attention

Lead output: a ranked watchlist

For each ship, the system shows how likely it is to send misleading reports, how uncertain that estimate is, and the evidence that supports it. The list helps a supervisor see where the drone’s attention should go next.

Per-ship belief
Beta parameters for the estimated deception rate.
Evidence timeline
Timestamped reports, visible checks, and mismatches.
Coverage and summary
Coverage statistics, a natural-language run summary, and a machine-scorable end record.

06 / What counts as success

Judge the estimate, not an imagined result

Primary metric

Posterior log-loss against hidden sampled pi

In plain words: does the estimated deception probability match the ship’s true simulated probability? Lower is better.

GitHub issue #21, primary metric section
Secondary metric

Top-k watchlist precision

In plain words: are the ships near the top of the watchlist actually among the most deceptive in the simulation?

Also report curves over time and terminal aggregates. Average results over at least 30 generated episodes.

GitHub issue #21, secondary metrics and protocol sections
Evaluation-only truth: hidden sampled pi is used by the terminal scorer after the mission. It is not a system input during execution. Planned comparisons include LLM+MiniZinc, LLM-only, random patrol, lawnmower, and oracle. GitHub issue #21, scoring and baselines sections
07 / What is not claimed yet

Useful limits to keep visible

No observed result

This is a planned experiment. It does not report a run, an improvement, or a winning baseline.

It does not include omission detection, noisy perception, multi-drone coordination, HITL, or cross-mission reputation.

GitHub issue #17, constraints; GitHub issue #21, constraints; docs/adr/0001-ship-event-discrepancy-detection.md:49–56
Open metric

Spec 1 has no separate aggregate detection threshold

The detection foundation has functional checks: load and validation, coverage for known ships, in-window/FoV behavior, fabricated-report detection, latching, and JSON-serializable additive information. It does not specify a mission-level detection-rate threshold or terminal criterion.
