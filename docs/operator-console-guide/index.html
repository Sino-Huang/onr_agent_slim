Using the ONR Operator Console

The Operator Console is a full-screen terminal UI that launches one mission at a time, shows what the agents are doing while it runs, and lets you cancel it cleanly. This guide covers a full session, from opening the console to recovering a run after a crash. Every screen image below is a real console render frame, committed under docs/design/operator-console/frames/.

1. What the console is

There are two programs. You only interact with the first one:

Operator Console (this TUI)

A Rust terminal app. You use it to pick a stack, type a Mission Intent, watch progress and cancel. It never starts simulators or agents itself.

Runtime Host

A local Python service (default http://127.0.0.1:8787). It starts and stops each run's Environment Stack, owns all run state and writes evidence under var/runtime-host/runs/<mission_run_id>/.

The launcher script starts a Host for you if none is running. Because the Host owns the run, closing or crashing the console does not stop the mission. See Recovery.

2. Before you start

  • Environment: the onr conda environment (the launcher activates it).
  • Model server: vLLM must be serving the configured model at http://127.0.0.1:11411/v1/models.
  • Sibling checkouts: onr_physical_runtime, the scenario inputs and the planner executables are needed even for simulated missions.
  • AirSim runs only: the Harbor engine and its settings, plus the sibling onr_solution producer. YOLO perception also needs yolo_weight/best.pt and ultralytics.
  • Terminal size: at least 100×30. Use 140×40 or larger to see the overview image and side panels; 160×45 works well for demos.
# one-time per shell
cd /data/ccu/sukaih/ONR/onr_agent_slim
source /home/sukaih/miniconda3/etc/profile.d/conda.sh
conda activate onr
curl --fail http://127.0.0.1:11411/v1/models   # is vLLM up?
bash scripts/vllm/start_vllm.sh                 # only if it is not

You don't have to check every prerequisite by hand. The console runs a preflight check and names exactly what is missing.

3. Start the console

./scripts/tui/start_operator_console.sh
# Low-resolution compatibility fallback, not for readable image labels:
./scripts/tui/start_operator_console.sh --image-protocol halfblocks
# Give a slow, cold Host start more time (default 60 s):
./scripts/tui/start_operator_console.sh --host-ready-timeout 120
OptionMeaning
--image-protocol auto|kitty|sixel|iterm2|halfblocks|off How world and camera images are drawn. auto queries the terminal. halfblocks is a low-resolution fallback. Readable maps and cameras require pixel graphics enabled throughout the terminal/multiplexer chain. off disables images. The ONR_CONSOLE_IMAGE_PROTOCOL environment variable sets the same option.
--host-ready-timeout SECSHow long to wait for a bootstrapped Host to become healthy.
--notify none|bell|desktop What happens when the stack becomes ready and planning starts, the stack fails, the run awaits a Human Decision, or the run ends. bell (default) rings the terminal bell; desktop also sends a desktop notification (OSC 9, or OSC 777 on VTE terminals and urxvt); none stays silent. In every mode the window title shows the run status, e.g. ONR ● running 00:12:04 · Planning or ONR ✖ stack_failed, and is restored on exit. Each event alerts once per run, and a restarted console never replays what already happened. Inside tmux the title is the pane title, a bell marks a background window, and desktop notifications need set -g allow-passthrough on (tmux 3.3+).
http://127.0.0.1:PORTConnect to a Host on a non-default port.

The first run compiles the release build, which takes a while. Warm it up before a demo. While the Host boots you'll see a spinner. Host output goes to var/runtime-host/host.log, and if the Host fails to start, the console prints the last 20 lines of that log.

4. Choose a stack and a Mission Intent

The Launch screen has four areas. Stack (top left) selects what to run. Preflight (top right) shows whether it can run. What this runs (middle) says in plain words what the selection starts. Mission Intent (bottom) is the plain-language task for the agents.

  1. Pick a preset. Press Tab to reach the Preset field and Enter to open the preset picker: every preset by name, with the highlighted one's description, the toggles it offers and the defaults it applies (↑/↓ move, Enter selects, Esc cancels). ←/→ still step through presets. mission1-harbor is the simulated stack, which still uses the real world model, planners, belief service and vLLM agents. mission1-airsim uses the real Harbor engine. Other presets: mission2, mission3, mission4, joint, joint24, joint34.
  2. Set the toggles. AirSim, Perception (off/ideal/yolo), Updates and Sim limit. An option marked ✗ is unavailable for this preset, and the console explains why. For example, ideal/yolo perception needs AirSim, and only mission1-airsim plays the recorded engine scene they need.
  3. Pick an AirSim mode. With AirSim on, Harbor always starts. With perception off, the world model runs on simulated information and AirSim follows it for visualization. With ideal or yolo, the scene clock synchronizes the world model to AirSim and the perception module feeds it.
  4. Read What this runs. It changes with every selection, using the Runtime Host's own descriptions: Mission (the goal, and that real LLM calls happen), Truth (simulated truth, or perception-fed truth), AirSim (nothing; the AirSim Follower visualizing the simulated world with no agent perception; or the annotated front camera) and Updates (what Mission time does: coordinator-driven, it pauses while the agents reason, so wall time runs ahead). Focus Updates to compare both update modes. An older Host sends no descriptions, so the panel is not shown.
  5. Wait for preflight. ✔ pass, ▲ warning (launch allowed), ✖ failure (launch disabled). Failures are listed first, then warnings, then passes; the panel title counts each. Press Tab to reach Preflight, ↑/↓ to pick a check, and Enter to read its full detail and hint. Press r to re-run it after fixing something.
  6. Write the intent. Type in the Mission Intent box. Enter inserts a newline here; it does not launch. Press F2 to insert a prepared prompt instead.
  7. Review. Press Alt+Enter (some terminals report Ctrl+Enter) to open the review screen.

5. Review and launch

Expect a long startup. The Host must bring the whole Environment Stack to readiness first. Simulated Mission 1 prepares surveillance planning views during startup, which can take noticeably longer than the physical runtime alone. Real missions run actual model inference and can take tens of minutes.

Overview: is everything OK?

The run card (status, mission, stack, timestamps), the latest Run Narrative, the Significant Activity feed and any Human Decision Requests.

The Run Narrative is refreshed in the background about every 30 s and once more when the run ends. It is labelled AI · non-authoritative: a model-written summary, not ground truth.

Its header says how old it is and what it covers: AI narrative · 42 s old · through record #763 · 18 newer. The age keeps ticking between updates; 18 newer means 18 operational records arrived after the last record the narrative covers, so newer authoritative state may disagree with it. Before the first narrative it reads coverage pending; the run's last attempt adds final, and a failed attempt reads unavailable. The Overview shows at most four lines; 2 opens Progress for the full text.

Human Decisions is a status-only view; it has no controls.

Progress: what happened, at three levels

Run Narrative → Mission Log Summaries → raw records. Each summary covers an exact range of operational records. Records that no summary covers yet appear under Live — not yet summarized. When the next summary arrives, they move under it without duplication.

The narrative header sits above the tree. Select the root (Run Narrative) to read the full text with its coverage (through record #763 · newest record #781) in the detail pane.

  • ↑/↓ select; ←/→ or Enter fold/unfold
  • f follow newest. Moving the selection pauses follow so you can read history.
  • i cycles the minimum importance, for example to show debug heartbeats
  • / search, Enter accept, n/N next/previous match
  • PgUp/PgDn scroll the selected-evidence detail

While the search box is open, typing is captured, so q, c and Tab are entered as text. Ctrl+C still exits.

Stack: the processes behind the run

Each prep step and service in this run's Environment Stack. Prep steps sit where they run: prepare steps above the services, post_ready steps below them, each with its measured duration once finished (✔ airsim-fixture done 0:03) or its time against the step budget while running. Services show readiness, port, PID, exit status and last log line. A ready service shows how long it took to become ready (in 1:18); a starting one shows time waited against its readiness budget (0:47 / 5:00) and, for the selected service, what it is Waiting: for. When the previous run of the same preset measured that service, Last run: shows its readiness time as history, never as an estimate. Below (or beside) is the selected row's log tail. Step history is read from the run's stack-status.json, so it is still there after a Host restart.

  • ↑/↓ choose a prep step or service
  • f follow the log; PgUp/PgDn scroll it

Waiting banner. While the run waits, a row under the phase stepper appears on every tab: the prep step or service being started, what readiness it still waits for, time waited against the budget and, if measured, the previous same-preset run's readiness (last run 0:27). A ▲ before the timer means 80% of the budget is used. During planning and execution the same row reports a live agent call, for example Waiting for the LLM · hyper-agent · ChatOpenAI · 0:12. The spinner moves while the console is alive; if the Host stops answering, the header shows host ▲ stale.

w: inspect the current wait. From any tab, w opens what the banner names at that moment: a starting service or running prep step opens this tab with that row selected and its log following; a live LLM or tool call opens 3 Agents with that invocation selected (following pauses, so newer calls do not move it). The banner ends with the hint, e.g. w: 6 Stack log.

AirSim engine start-up and real LLM calls take minutes; a moving spinner with a growing timer is normal. Press w and read the log tail if the timer nears its budget.

Artifacts: files the run produced

Planner files, accepted statecharts, reports and verification logs, with source, size and media type. Like Agents, the list scrolls to keep the selection visible and shows its position and ▲/▼ overflow marks.

  • ↑/↓ select, Home/End first/last, Enter opens the paged inspector
  • In the inspector: ↑/↓ and PgUp/PgDn scroll the wrapped lines of the current page, Home/End jump to its first/last line; →/n next and ←/p previous 4096-byte page; Esc closes. The status row reads line 65/84 · bytes 0-4095 of 51234: the first visible line of the page and the page's inclusive byte range.

8. When a mission is rejected

If the intent is not an operational objective the vehicles can carry out (try "buy me a coffee" from F2), the Hyper Agent rejects it. A prominent card shows the actual reason, the intent, the stage and how much work was done.

  • Enter shows run details. In 3 Agents you can see the recorded reject_mission_intent tool call.
  • e returns to Launch with the same preset and toggles so you can write a new intent. It becomes available only after cleanup (summary flush and stack teardown) has finished.
  • e works the same way after any finished run, not only rejections.

9. When the stack or worker fails

A run can also end because its infrastructure failed: a stack service crashed or never became ready (stack_failed), the Run Worker raised (worker_failed), or the Runtime Host was interrupted while the run was active (host_interrupted). The console then shows a failure card with a double red border, so it never looks like a mission rejection. It lists only what the Host recorded: the stage, the sanitized reason, the failed service, the last phase step that completed, and whether the stack is torn down.

  • l opens the relevant log in the Artifact inspector at its tail: the failed service's log for stack_failed, the Run Worker log (worker-log, with the traceback) otherwise. Scroll up with ↑/PgUp, step back a byte page with ←; Esc returns to the card.
  • 2 opens Progress, to see how far the run got.
  • y copies the run id and the Run Root path to the clipboard with an OSC 52 escape. Your terminal decides whether to accept it; inside tmux it needs set -g set-clipboard on (and, for tmux 3.3+ passing it to the outer terminal, allow-passthrough on). Both values are printed on the card anyway.
  • Enter (or any tab key) dismisses the card; l and y keep working afterwards.
  • e starts a new intent only after cleanup: while the stack status still lists a service as starting or ready (or has not arrived), it says so and stays on the run.

An older Host (API before 1.5) names no log and no Run Root: l then opens the failed service's log from the stack status, or the worker log, and says so; y copies the run id alone.

10. Cancel, exit or detach

c then Enter: cancel the run

Stops this run's worker and its Environment Stack. The console stays open and the tabs stay usable while the waiting banner shows each service stopping. Teardown can take up to about 9 s.

q or Ctrl+C: managed exit

Quits the console. If you own an active run, the console asks you to confirm cancellation first. A second Ctrl+C does not silently abandon the run.

Ctrl+Q: detach

Quits without cancelling. The Host, the run and your owner session keep going, and relaunching the console reconnects you to the same run.

The terminal receipt

When a run ends, the Mission Run panel becomes the run's receipt. Each row comes from its own authority, so a green lifecycle never reads as mission success:

  • Lifecycle: what the Run Worker did (succeeded, failed · worker_failed, cancelled · cancelled_by_owner). It is not a verdict on the mission.
  • Finished adds the wall duration; Final is the last FSM state, plan revision and Mission time the evidence recorded (the latest FSM status record and environment data).
  • Audit is PASS or FAIL only when scripts/audit_live_demo.py wrote live-acceptance.json into the Run Root. Without that file it reads not recorded (no audit artifact), whatever the lifecycle says.
  • Teardown / Services / Harbor: the cleanup receipt from the stack.
  • Export: press x and the Host writes the receipt (metadata plus references to the Run Root's evidence files and logs) to <run root>/mission-run-receipt.json and shows the path. Pressing x again overwrites the same file. Each export re-reads the audit and refreshes the panel, so after running the audit press x again and both carry its verdict. Only the console that launched the run can export.

Run history: earlier runs, read-only

Press F3 on Launch or on the Run screen to list the Host's Mission Runs, newest first: start time (UTC), preset and toggles, lifecycle status and classification, wall duration and run id. The list never shows a Mission Intent. s cycles a status filter (all, succeeded, failed, cancelled, active) and p a preset filter over the loaded rows; moving past the last row loads the next older page. A run whose Run Root was removed is marked ✖ no root, and Enter on it says so instead of opening an empty run.

Enter opens a run read-only in the normal seven tabs with a HISTORICAL badge in the header. Cancel, export and new-intent keys are refused; Esc returns to the current run, or to Launch. Viewing history never changes which run this console owns: the current run keeps being polled, and its bell and title alerts still fire while you read an older run.

The Host rebuilds a run it has not served since it started from the run's files on disk. For a long run the first read can outlast the console's 5 s request limit (17 s for a 28-minute run). Until the run's overview arrives the header says loading from disk and the footer counts the seconds and any reads that timed out and are being retried. That is loading, not an error; any other failure still shows as Host … poll failed. Notices raised while you read an older run stay with it: Esc drops them and brings back the current run's own.

Presentation layout (F4)

Press F4 on the Run screen to keep the audience on the scene: the selected World source fills the left (scaled up), with the AirSim Follower and annotation disclosures under it; one evidence card fills the right; the mission title, the wall clock (UTC), the run's wall time and Mission time sit on top. v cycles the card between the milestone (the current phase step and the Progress selection), the Belief/Context entity and the Agents invocation; the card shows those tabs' existing selections and never rotates on its own. s changes the World source. F4 returns to the tab you came from; a tab key, w or the failure card's l also leave the layout.

p freezes the display: the frame, the card, the phase stepper and the clocks hold and the clock row reads FROZEN AT <wall> · t=<mission>. Freezing is display-only: every section keeps polling, the frame is held with the World tab's p pause, and p again shows the latest evidence. The title row and the alert rows stay live: a failure (with its failure card), a Human Decision Request and a stale or offline Host break through, frozen or not. A historical run (F3) can be presented read-only; its alert rows follow the current run.

Don't kill the Host to end a demo. Use c or q. A killed Host cannot resume its run. See below.

11. Recovering after a crash

What happenedWhat survivesWhat to do
Console killed (even kill -9), terminal closed, or Ctrl+Q The Host and the run keep going. Your Console Session is saved at ~/.local/state/onr/operator-console/session.json. Run the launcher again. It reconnects to the same Host and recovers ownership of the run, including the ability to cancel it.
Your saved run is gone, or the Host is running a newer run Nothing to recover The console returns to Launch and does not take over someone else's run.
Host killed The run cannot resume Restart the Host, for example by running the launcher. It removes the leftover processes it can prove belong to that run and records the run as failed · host_interrupted.

A console that reconnected to an already-running Host never stops that Host when it exits. Only the console that bootstrapped the Host does.
